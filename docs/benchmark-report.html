DuckDB vs jq Benchmarks

One pipeline turns tables of trade data into clean, nested JSON. We ran it on the same data with DuckDB and with jq, measured every step, and checked that both produced the same result. This report explains each benchmark in plain words.

Summary

29×jq took 29 times longer than DuckDB for 1 million trades (5 min 14 s vs 11 s).
20×DuckDB was still 20 times faster when we let it use only one CPU core, like jq.
4× lessjq used about four times less memory (632 MB vs 2.6 GB at 1 million trades).
10 of 10benchmark comparisons produced the same JSON from both engines. We checked every time.

Use DuckDB for this kind of work: big tables, joins, links between rows, and totals. Keep jq for small jobs on JSON files. DuckDB’s higher memory use can be fixed: with two settings it used 60% less memory and ran twice as fast (Benchmark 11).

Words used in this report

A database engine that runs inside your program. It reads CSV and Parquet directly and runs SQL. It works on whole columns at once and can use all CPU cores.
jq
A command-line tool for JSON. It reads one JSON record, changes it, writes it out, then reads the next. It uses one CPU core.
CSV
A plain text table. Commas separate the values.

Input rows divided by total time. Higher is better.

A row that points to an earlier row. Example: an amendment points to the original trade.
Forward reference
A row that points to a row further down the file. A stream reader has not seen it yet.

Duplicates, missing values, wrong formats and broken links. The test data has all of them on purpose.
Verification
An automatic check that both engines produced the same JSON for the same input.
Event

Worker process
A separate program that does the heavy work, so the API stays quick.

The services and how they work

The system has three services: Dataset, Pipeline and Benchmark. They share one backbone: an event bus, a pool of worker processes and a state keeper. Three rules shape every workflow:

  • Answer first, work later. A request is saved and answered at once. The work itself starts in the background.
  • Talk through events. A service never calls another service directly. It announces what happened, such as “DatasetReady”, and every part that cares reacts.
  • Heavy work runs in a worker process. Each job gets a fresh process, so jobs never share memory and the system stays responsive.
Service 1

Dataset service

Creates or accepts the input data and keeps it ready for reuse.

  1. Request. You ask for a size, for example 1 million trades, or you upload your own CSV or Parquet files.
  2. Reuse check. The dataset’s name comes from its settings: size, seed and amount of dirty data. If that dataset already exists, it is reused and nothing is generated again.
  3. Pending. The service saves a “pending” record and announces DatasetGenerationRequested.
  4. Build in a worker. A worker builds the five tables, adds the planned problems (duplicates, gaps, broken links, loops) and writes Parquet and CSV files. For uploads, the worker instead checks that every required column exists and counts the rows.
  5. Ready or failed. The service announces DatasetReady with row counts and file sizes, or DatasetFailed with the reason.

Leaves behind: one folder per dataset with the data files and a manifest. The same settings always produce exactly the same files, so any test can be repeated.

Service 2

Pipeline service

Cleans, validates and transforms one dataset with each chosen engine, then proves the results match.

  1. Request. You pick a ready dataset, the engines, and optional filters: a trade-date range, instrument types, a minimum size, or latest versions only.
  2. Plan. The service saves one comparison and one run per engine, all “queued”, and announces ComparisonRequested.
  3. Run each engine. The orchestrator sends one engine at a time to a fresh worker. Inside the worker, the pipeline runner drives the five stages in a fixed order while a monitor measures time, CPU and memory. Every stage start and finish is announced, so progress shows live.
  4. Handle failure. If a stage fails, that run stops, its half-written files are deleted and the error is saved. The other engine still runs.
  5. Verify. When all runs have finished, a verification job compares the engines’ outputs document by document.
  6. Complete. The service announces ComparisonCompleted with the timings, the slowdown factor and the verdict.

Leaves behind: for each engine, the finished trades, the rejected trades with reasons, the exposure totals and a data-quality report.

Service 3

Benchmark service

Measures both engines across several sizes without the runs disturbing each other.

  1. Request. You choose the sizes (for example 5 thousand to 1 million trades), the engines and the file format.
  2. Prepare data. For each size, smallest first, it makes sure the dataset exists. If not, it asks the Dataset service and waits until the data is ready.
  3. Compare. It runs a full comparison through the Pipeline service workflow and waits for it to finish.
  4. Free disk. It deletes the large output files. Timings, quality reports and exposure totals are kept.
  5. Next size. Only then does the next size start. Two sizes never run at the same time, so they never compete for CPU or memory.
  6. Report. When the last size is done, the result table is saved.

Leaves behind: a results table for every size and engine, saved as a readable report and as data.

How each engine moves data

This is the main reason for the speed gap. DuckDB keeps the data in memory, in columns, from start to end. jq can only read JSON text, so each step reads a file, parses every line, and writes a new file. Any step that needs to “look at everything” needs an extra pass.

How we measured

  • Same input, same rules. Both engines read the same files and apply the same 13 rules in the same order.
  • Same output, checked. After each comparison, a checker matches the two outputs document by document. Above 200,000 rows it fully compares a fixed sample of about 50,000 documents, and still checks every row count and every key.
  • Same stopwatch. One monitor wraps every stage. It records wall time, CPU time and peak memory every 50 ms, including child processes.
  • Clean process per run. Each run starts in a fresh worker process, so memory left over from one run does not affect the next.
  • One at a time. Benchmarks run sizes and engines one after another, never in parallel.
  • Fair to jq. jq code streams wherever it can, never loads the whole trade file at once, and was tuned after profiling (see Benchmark 9).
  • Single runs. Each number comes from one run. Benchmark 8 shows how much a repeat run can differ.

Deep nesting and long chains

Question
Does one engine break when links get very deep or very long?
Setup
Same 50k size, three versions of the data: normal (parents 7 levels deep, up to 5 versions per trade), deep (parents 200 levels deep), and long chains (up to 100 versions per trade).

What it means. The difference is in how each engine expresses the work, not in how it scales:

  • DuckDB has no data type for “an object that contains itself”, so a parent chain of unknown depth cannot be a normal typed column. We built that one column as JSON inside a recursive query. It works, but that column loses its types.
  • DuckDB recursive queries can loop forever on a cycle. We start from the top parents and walk down, so loops are never entered and are flagged instead.
  • jq handles nesting naturally with recursion, but needs a “seen” list to stop on cycles, and needs the full set of version links in memory to follow chains.

Tuning jq

Question
Is jq slow because of how we wrote it?
Setup
We wrote the same aggregation three ways and timed each on the same 100,000 documents.

At 1 million trades this tuning cut jq’s aggregate stage from 188 s to 47.5 s. A smaller test showed one more rule: updating a group with .[$k] |= … was 1.6× slower than updating its fields directly. The final code uses the fastest form everywhere. Even tuned, jq is far behind DuckDB, because every jq pass still has to parse JSON text: a pass that only parses and counts the 1M-row output already takes 18 s.

Fixing DuckDB’s memory use

Question
Can DuckDB use less memory without losing its speed?
Answer
Yes. Two settings cut peak memory by about 60% and made the run twice as fast. A third brings it near jq’s memory.

Where the memory goes. Memory peaks in the transform stage. By default, DuckDB first builds the full nested result (981,001 documents) as a table in memory, then writes it to JSON. That one table is most of the 3 GB.

We tried each setting on its own, then together: 12 runs in one session, one after another. Automated tests check that every setting produces exactly the same JSON as the default. The default here (3.2 GB, 6.3 s) differs from Benchmark 1 (2.6 GB, 11.0 s), which ran when the disk was almost full and writing was slower; compare settings within this benchmark only.

SettingWhat it doesEnvironment variable
Lean mode (new in this POC)Streams the JSON straight out of the query instead of building the table first. Drops tables as soon as no later stage needs them.POC_ENGINE__DUCKDB_LEAN=true
Unordered outputLets DuckDB write rows in any order. It no longer has to hold rows back to keep them in file order.POC_ENGINE__DUCKDB_PRESERVE_INSERTION_ORDER=false
Memory limitA hard cap. Above it DuckDB moves data to temporary files on disk (“spilling”).POC_ENGINE__DUCKDB_MEMORY_LIMIT=1GB
On-disk databaseKeeps tables in a database file instead of in memory.POC_ENGINE__DUCKDB_STORAGE=disk
Fewer threadsFewer cores working at once, so fewer buffers in memory.POC_ENGINE__DUCKDB_THREADS=2

What each result means:

  • A memory limit alone fails. With 1 GB and default settings, DuckDB stopped with “Out of Memory”, because the full nested table cannot fit. The limit only works together with lean mode, which never builds that table.
  • Lean mode alone saves memory but is slower (7.9 s). Keeping file order makes the streamed output wait, and the aggregate stage has to rebuild the documents. With unordered output, it becomes the fastest run of all.
  • An on-disk database alone does not help (3.4 GB, 13.7 s). The peak is in the query that builds the result, not in the stored tables, and the disk reads and writes add time.
  • Two threads saved about 20% memory (2.6 GB) at the same speed.
Two things to watch. First, spilling needs free disk. A run with only a 512 MB limit failed with “No space left on device” on the nearly full test disk, so we could not measure it. Second, unordered output changes the order of rows in the JSON file (the content is the same), and if two duplicate rows are not identical, the “first one wins” rule follows read order instead of file order. Our duplicates are exact copies, so results did not change.

Other ways to cut memory (not measured here): write Parquet instead of JSON for files that only machines read; process the data in chunks, for example one month of trades at a time, since the lookup tables are small; or use a machine with more RAM, which is often the cheapest fix.

Better alternatives for this scenario

Our job is: read tables (1 to 5 million rows) on one machine, clean and check them, follow links between rows, build nested JSON, and add up totals. These are the realistic options. We did not benchmark them in this POC; the notes come from each tool’s documented features.

Verdict. For this scenario, DuckDB with lean settings is the best fit: fastest, simplest (plain SQL), and now modest on memory. Polars is the closest alternative if you prefer Python DataFrames. Move to Spark only when the data outgrows one machine. A faster jq clone does not fix jq’s real problem, which is the extra passes needed to follow links between rows.

What about 5 million rows?

The 5M dataset is made and saved (76 MB Parquet, 553 MB CSV), but we did not run it. Each engine writes about 1.2 GB of JSON per million trades, so a 5M comparison needs about 20 GB of free disk. The test machine had less than 5 GB.

A rough guess from the measured speeds: jq ≈ 26 minutes (it stays near 3,200 rows per second), DuckDB ≈ 1 minute. These are estimates, not measurements. Free about 20 GB and run make benchmark with 5m to get real numbers.

Hard limits, and what to do instead

Things each tool cannot do on its own. Most have a workaround, which is why the matrix above rates many of these scenarios as “Limited” rather than “Cannot”.

jq cannot…

  • —Read CSV or Parquet.Convert to NDJSON first, for example with DuckDB.
  • —Use more than one CPU core in a run.Split the file and run several jq processes, only for per-record steps.
  • —Move data to disk when memory runs out.Keep the state small, or use a database engine for that step.
  • —Do exact decimal maths.Calculate money in another tool, or work in whole cents.
  • —Write Parquet or other column files.Write JSON, then convert with another tool.
  • —Check a link to a row it has not read yet, in one pass.Read the data twice: first collect the ids, then check (as this POC does).

DuckDB cannot…

  • —Store an object that contains itself as a typed value.Build that part as JSON in a recursive query (as this POC does).
  • —Let several processes write one database file at the same time.Funnel writes through one service, or use a server database such as PostgreSQL.
  • —Spread one job over several machines.Use Spark or a similar engine once data outgrows one machine.
  • —Process an endless stream continuously.Run the same query on small batches, for example every minute.
  • —Stop a looping recursive query by itself.Design the query so loops are never entered, or track the path and stop on repeats.
In short: DuckDB is strong wherever the job needs the whole dataset at once: joins, links between rows, sorting, grouping, big volumes. jq is strong on single records: uneven shapes, deep nesting, small memory, endless streams and quick shell commands. This project needs the whole dataset at once, which is why DuckDB fits it better.

How the codebase is organised

The code follows clean architecture: the inner layers do not know about the outer ones. Each engine is a plug-in behind one interface, so adding a third engine means writing one class.

app/
├── domain/          data models, events, interfaces, the 13 rule codes   (no I/O)
├── application/     services, orchestrators, pipeline runner, verification, reports
├── engines/

Quality checks: 34 automated tests (engine parity, edge cases, generator, full API flow), strict type checking with mypy, and linting with ruff.

Run it yourself

make install      # install dependencies (needs jq on PATH)
make run          # API + dashboard on http://127.0.0.1:8000
make datasets     # create 5k, 50k, 500k, 1M and 5M (same data every time)
make benchmark    # Benchmarks 1-4, 8, 10 (5k to 1M)
make scenarios    # Benchmark 6 (deep nesting, long chains)
POC_ENGINE__DUCKDB_THREADS=1 uv run python -m app.cli benchmark --sizes 1m --engines duckdb   # Benchmark 5
POC_ENGINE__DUCKDB_LEAN=true POC_ENGINE__DUCKDB_PRESERVE_INSERTION_ORDER=false \
  uv run python -m app.cli benchmark --sizes 1m --engines duckdb --no-verify                    # Benchmark 11

Every benchmark also saves a Markdown and JSON report in data/reports/.
