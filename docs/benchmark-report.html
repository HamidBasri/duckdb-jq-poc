My take

Use DuckDB for this kind of work. It reads CSV and Parquet directly, uses every core and follows links between rows with plain joins. jq is still handy for small fixes to JSON files, but it has to read the data several times to follow those links, and that is where most of its time goes.

  • Speed7 to 40 times faster with DuckDB, depending on size
  • Memoryjq is leaner by default; two DuckDB settings close most of the gap
  • Hard dataDeep trees and long amendment chains slow both down by the same amount
  • OutputIdentical from both engines in every run

Realistic, messy trade data

The data is fake but built like a real feed: trades, counterparties, instruments, books and FX rates, all pointing at each other. About 2% of the rows have problems on purpose, and the same settings always produce the same files.

Speed

DuckDB is 7 to 40 times faster

The gap grows with the data. jq stays at about 3,000 rows a second whatever the size, while DuckDB gets faster as there's more to do.

DuckDBjq

At 1M rows the gap drops to 29×. That's DuckDB slowing down while it wrote 1.2 GB of JSON to an almost full disk, not jq catching up.

Numbers
One core each15.6 s

DuckDB limited to a single thread did 1M rows in 15.6 s, still 20× faster than jq. The speed comes from working on columns in memory, not from extra cores.

CSV instead of Parquet+0.08 s

Reading CSV added 0.08 s to DuckDB's ingest and 0.16 s to jq's at 500k rows. The input format barely matters here.

Running it again±17%

A second run of 5k to 500k differed by up to 17%, but the gap stayed put: 40.0× and 39.9× at 500k. Treat small differences as noise.

Where time goes

jq struggles most where rows depend on other rows

To check that every link points at a real trade, jq first reads all the trade ids, then reads everything again. DuckDB does the same check with one join in 0.2 seconds.

Memory

jq is leaner, until you tune DuckDB

jq streams records, so it only keeps what each pass needs to remember. By default DuckDB builds the whole nested result in memory before writing it out, which is where its 2.6 GB peak comes from.

Two settings change the picture. Lean mode writes the JSON straight from the query and drops tables once no later stage needs them. Unordered output lets DuckDB write rows as soon as they're ready instead of holding them to keep file order. I tried each setting on 1M rows, alone and together.

A memory limit on its own doesn't help: at 1 GB the default mode ran out of memory, because the full result still has to fit. Spilling to disk also needs free disk. One run with a 512 MB limit failed because the disk filled up. Unordered output changes the order of rows in the file, which didn't matter for this job.

Settings: POC_ENGINE__DUCKDB_LEAN=true, POC_ENGINE__DUCKDB_PRESERVE_INSERTION_ORDER=false, optionally POC_ENGINE__DUCKDB_MEMORY_LIMIT and POC_ENGINE__DUCKDB_STORAGE=disk.

Hard data

Deep trees and long chains don't break either one

I made two harder versions of the 50k dataset: parent chains 200 levels deep, and trades amended up to 100 times. Both engines slowed down by about the same amount.

Where they differ is how naturally they express it. DuckDB has no type for an object that contains itself, so I built the nested parent as JSON inside a recursive query, and I had to start from the top of each tree so loops were never entered. jq handles nesting with plain recursion but needs a list of visited ids to stop on loops.

Tuning jq

How you write jq matters a lot

I wrote the same aggregation three ways and timed each one on 100,000 output documents.

At 1M rows the rewrite took jq's aggregate stage from 188 s to 47.5 s. Even so, every jq pass has to parse JSON text: just reading and counting the 1M-row output takes 18 s, which is more than DuckDB needs for the whole job.

Things jq can't do

  • Read CSV or ParquetConvert to NDJSON first, for example with DuckDB.
  • Use more than one core in a runSplit the file across several jq processes, for per-record steps only.
  • Move data to disk when memory runs outKeep what each pass remembers small, or use a database for that step.
  • Exact decimal mathsWork in whole cents, or calculate money elsewhere.
  • Check a link to a row it hasn't read yetRead the data twice: collect the ids, then check.

Things DuckDB can't do

  • Store an object that contains itself as a typed valueBuild that part as JSON in a recursive query.
  • Let several processes write one database file at onceSend writes through one service, or use a server database.
  • Spread one job over several machinesMove to Spark or similar once the data outgrows one machine.
  • Process an endless stream continuouslyRun the same query on small batches.

How the app works

Answer first, work in the background

A request is saved and answered straight away. Services announce what happened as events, orchestrators pick those up, and worker processes do the heavy lifting, two jobs at a time by default.

Datasets

  1. Ask for a size, or upload CSV or Parquet files.
  2. If that exact dataset already exists, it's reused.
  3. A worker builds the tables and writes Parquet and CSV, or checks an upload's columns.
  4. The dataset is marked ready, with row counts and sizes.

Pipeline

  1. Pick a dataset, the engines and any filters.
  2. Each engine runs in turn through the five measured stages.
  3. If a stage fails, that run stops and its partial files are deleted.
  4. A checker compares the outputs, and the result shows timings and the verdict.

Benchmarks

  1. Choose the sizes, smallest first.
  2. Missing datasets are generated and waited for.
  3. Each size runs a full comparison, then its big output files are deleted.
  4. Sizes never overlap, so they don't fight over CPU.

There's also a trade tracker. After each run it records where every input row ended up: delivered, rejected, removed as a duplicate or filtered out. You can search any trade and see its path through the stages with real timestamps, and its record before and after.

Run it

Try it yourself

make setup       # check tools, install, create small datasets, run the tests
make run         # dashboard on http://127.0.0.1:8000, tracker on /tracker
make benchmark   # 5k to 1M rows, both engines
make scenarios   # deep trees and long chains

All numbers come from one run per size on an Apple Silicon laptop with 10 cores and 16 GB of RAM, using Parquet input. The 5M dataset is in the repo's generator but I didn't run it: each engine writes about 1.2 GB of JSON per million rows, so 5M needs around 20 GB of free disk. My rough guess from the measured speeds is 26 minutes for jq and about a minute for DuckDB.
