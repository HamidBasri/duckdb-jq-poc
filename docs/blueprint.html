Start

The whole project in one minute

Eight sentences you can say out loud, in this order. Each one is explained further down the page.

  1. The questionWhich tool is better at turning big tables of trade data into clean, nested JSON: DuckDB, a SQL database that runs inside the app, or jq, a command-line tool for JSON?
  2. The dataFive linked tables: trades, counterparties, instruments, books and FX rates. A generator makes them with mess added on purpose, or you upload your own CSV or Parquet files.
  3. The workBoth tools run the same five stages: ingest, clean, validate, transform and aggregate.
  4. The resultEach valid trade becomes one nested JSON document. Bad trades go to a rejects file with every reason. Money at risk is added up per parent company.
  5. The proofA checker compares the two tools' output document by document. Every run so far matched.
  6. The answerDuckDB was 7 to 40 times faster, from 5 thousand to 1 million trades. jq used less memory by default.
  7. The appA dashboard to create datasets, run one or both tools, benchmark sizes, read the raw and output data, fix values as new versions, and set rules that later runs follow.
  8. The designA request is answered at once. Heavy work runs in separate worker processes. Everything that happens is announced as an event, so the page updates live.

Data

Versions and edits

You never change a dataset's files. To fix something, you save a new version: a full copy with the fix applied. The original stays exactly as it was, so you can always go back and compare.

  • Edits point at row numbers in the file you edited (the parent). Row 1 is the first data row, not the header.
  • A version of a version carries everything before it: v3 above has the renamed columns from v2 plus its own edits.
  • Deleting a dataset deletes only that one. Versions made from it are full copies, so they keep working. Finished runs on it are kept too.
  • Fix columns is offered on uploads and their versions. Edits work on any dataset that has files, generated ones included.
  • An edit fixes one value in one dataset. To fix the same value everywhere, turn it into a correction rule (see Rules you can change).

Behaviour

The pipeline, step by step, in both engines

Both engines do the same five stages and write the same output files. DuckDB keeps everything in tables in memory. jq passes NDJSON files from one program to the next. This is where the speed gap comes from.

  • Follow a lane left to right to see one engine. Arrows into the middle lane are the moment an output file gets written.
  • Correction rules are applied in the read step of ingest, and that read step is the same SQL for both engines (jq's input is written by a DuckDB COPY). So both engines see exactly the same corrected values.
  • Switched-off rules are removed from each trade's list of errors in validate. DuckDB filters the list in SQL; jq gets the list of switched-off codes as an argument. A trade with no errors left is valid.
  • Rejects are written as soon as validate finishes. That's why the trade tracker can show rejected rows before the run ends.
  • In lean mode, DuckDB streams out_trades as a view and drops tables early. That nearly halves its memory at 1M rows.
Behaviour

Behaviour

Rules you can change

Two kinds of rule live on the Rules tab. Correction rules change a value while the data is read. Validation switches turn a reject rule off. Both are saved together as one numbered version; new runs use the newest one, and every run keeps the one it used.

How a correction rule matches

TableColumnWhen the value isChange it toWhat happens
tradessideHOLDBUYHOLD and HOLD become BUY (spaces around the value are ignored). hold does not match: case matters.
tradescurrencyemptyUSDA missing or blank currency becomes USD, before clean would fill it from the instrument.
counterpartiescountryUKGBEvery counterparty with country UK gets GB, in every dataset, in new runs.
tradesprevious_trade_idNONEemptyLeaving "Change it to" empty empties the field. Here a NEW trade that wrote NONE as its earlier version no longer points at a trade that doesn't exist.
  • A rule compares the whole value. It can only name the expected columns of a table, and there can be only one rule per table, column and value.
  • Each rule has its own on/off switch, so you can pause it without deleting it.
  • The trade tracker applies the same corrections to trade ids, so its rows still line up with the run's output.
  • Switching a reject rule off keeps the trades whose only problems were switched-off rules. They are delivered like any valid trade, and the code no longer appears in the quality report.
  • tests/test_parity.py switches each of the five rules off, on data built to break it, and checks both engines still give the same output. A rule only becomes switchable once it passes this test.

Using it

Dashboard screens

Seven tabs for looking, four side panels for doing, two dialogs, and a separate page for single rows. Forms never sit on a tab; they open from a button.

Tabs

  • Overview: latest result, 4 key numbers, latest benchmark chart, what's running, recent runs
  • Datasets: every dataset with its versions nested under it; per row: view data, Run, Benchmark, Fix columns, Delete
  • Data: "Input tables" pages through a dataset's raw rows, 50 at a time; click a value to change it, or the bin to remove a row, then "Save as vN". "Pipeline output" pages through a run's trades, rejects or exposures, under a line that names the run (number, engine, dataset, start time, benchmark, rules version, filters); click a row for the full JSON
  • Runs: one row per run, named "Run 12 · 50,000 trades"; click for stage bars, data quality, output files and the rules version. "Browse" opens the output in the Data tab, "Track rows" opens the tracker
  • Benchmarks: one row per benchmark; click for the chart and stage table
  • Rules: correction rules, the 13 reject rules with on/off switches (locked ones say why), a save bar with a note, and every saved version
  • Activity: live log of every event, in plain words

Side panels

  • New dataset: generate (size and settings) or upload files
  • New run: dataset, engines, source format, checks, filters
  • New benchmark: sizes, settings, engines, keep files
  • Fix columns: expected column, your column, sample values; saves a new version

Dialogs and messages

  • Confirm: says exactly what will be deleted or thrown away
  • Output preview: first documents of a file, with a download link
  • Notifications: short confirmations or errors at the bottom right
  • Unsaved changes: on the Data tab, a list of your edits with Undo, "Make it a rule", Discard and Save

Separate page

  • Trade tracker (/tracker): pick a run, filter rows by fate, search a trade id, see one row's journey with before and after values

Words

Glossary

Every word used on this page, in one or two plain sentences.

The data

Trade
One deal: who bought or sold what, how much, at what price, on which date. One row in the trades table.
Counterparty
The company on the other side of the trade. A company can belong to a parent company.
Ultimate parent
The top company of a counterparty's tree. Exposure is added up per ultimate parent.
Instrument
The thing that was traded, such as a bond or an option. Some are based on another one, their underlying.
Book
The desk and trader that own a trade.
FX rate
How many US dollars one unit of a currency is worth. Used to turn every amount into dollars.
Amendment chain
The versions of one trade: NEW, then AMEND, maybe CANCEL. Each points at the one before.
Notional
Quantity times price: the size of a trade in money. notional_usd is the same in US dollars.
Exposure
Money at risk with one parent company, from the latest version of each trade, cancellations skipped. Gross adds up sizes; net counts buys as plus and sells as minus.
Dataset
One set of the five tables, generated or uploaded, kept as files with a manifest.json that describes them. A generated one is named by its size plus any setting that isn't the default ("50,000 trades · tree 200"); an upload by its number ("Upload 2").
Dataset version
A new copy of a dataset with fixes applied: renamed columns, changed values or removed rows. The original never changes.
Expected columns
The column names the pipeline needs for each table. An upload that lacks them fails until you fix its columns.
CSV / Parquet
CSV is plain text, one row per line. Parquet stores data by column, compressed, so it is smaller and much faster to read.
NDJSON
One JSON document per line, so a file can be read one document at a time.

The pipeline

Pipeline
The five stages that turn the input tables into the output files.
Ingest
Reads the five tables, every column as text, and applies correction rules.
Clean
Trims spaces, fixes spellings and formats, turns text into dates and numbers, drops exact duplicate rows, fills gaps it safely can.
Validate
Checks each trade against the reject rules that are on, and lists every problem it has.
Transform
Joins the tables, walks the company trees and amendment chains, and builds one nested document per trade.
Aggregate
Adds up exposure per parent company.
Reject
A trade that broke at least one reject rule. It goes to rejects.ndjson with every reason.
Warning
A note on a trade that was kept, such as "currency filled in from the instrument".
Correction rule
"In this column, when the value is A, use B instead." Applied while reading, in every new run, on every dataset.
Validation switch
Turns one reject rule off for new runs. Trades whose only problems were switched off are kept.
Locked rule
A reject rule that can't be switched off, because a later stage needs the value it checks.
Rules version
A saved set of correction rules and switches, numbered 1, 2, 3 … Version 0 is the defaults. Each run keeps a copy of the one it used.
Run filters
Optional limits on which valid trades are written: trade dates, instrument types, minimum size in dollars, latest versions only.
Row fate
Where an input row ended up: delivered, rejected, duplicate or filtered out.

Running and measuring

Engine
One way of running the pipeline: DuckDB (SQL) or jq (JSON programs).
Run
One dataset through the pipeline on one or both engines, then the output check. The code calls it a comparison.
Run number
The name every run gets, such as "Run 12". It counts up and is never reused, so it always points at one run. Benchmarks and uploads are numbered the same way.
Pipeline run
One engine's part of a run, with its own stage times and output files.
Benchmark
Several sizes, one run each, one after another, to see how each engine scales.
Output check
Compares both engines' files document by document, matched by key. "Match" means the same documents; numbers may differ by at most 0.011, which covers rounding to cents.
Sample
Above 200,000 documents the check compares about 50,000, picked by key so both sides pick the same ones.
Wall time
Time on the clock.
CPU time
Time added up over all cores. More than wall time means several cores worked at once.
Peak memory
The most memory a process used at any moment (peak RSS).
Slowdown
jq's time divided by DuckDB's time, for example "29× longer".
Row tracker
After a run, records the fate of every input row. The trade tracker page reads it.

The code

Clean architecture
Code in layers, where inner layers know nothing about outer ones. Here the domain knows nothing about FastAPI, DuckDB or files.
Domain
The ideas of the app: records, events, interfaces and rule codes, with no libraries.
Port
An interface the domain defines, such as "something that can save records".
Adapter
A real class that does what a port describes, such as JsonFileRepository.
Composition root
bootstrap.py: the one place that creates every object and plugs adapters into ports.
Service
The front desk for one kind of request: checks it, saves it, announces it, answers.
Event
A small record of something that happened, such as RunFinished.
Event bus
Hands each event to everything that subscribed to it, in a fixed order.
Orchestrator
Listens for "…Requested" events and runs the long work in a worker process.
Projector
Turns events into saved records. The only place a status changes.
Worker process
A separate Python process for heavy work. A fresh one per job keeps memory numbers clean and a crash contained.
Repository
Saves and loads one kind of record; here, as JSON files.
SSE
Server-sent events: one long HTTP response the server keeps writing events into. It's how pages update live.
202 Accepted
The HTTP answer for "got it, working on it in the background".
Pinned jq
The project runs one exact jq version, 1.8.2, kept in .tools/. Other versions can lack functions the jq programs use (macOS's own jq has no trim), so the jq engine refuses them.
Parity test
A test that runs both engines on the same data and checks they give the same output.
