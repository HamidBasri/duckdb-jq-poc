DuckDB vs jq · how it is built

The trade pipeline in ten minutes

The app takes messy trade files, cleans and checks them, and writes each trade as nested JSON. It does this twice, once with DuckDB and once with jq, and compares the two. This page explains it in three parts, from the folders up to the ideas.

Part 2 · The design

Ask, announce, work in the background

Nothing heavy happens inside a web request. The request saves a record, announces an event, and returns at once. Other parts hear the event and do the work in separate processes.

One run, step by step

  1. You askThe browser sends POST /api/comparisons with a dataset and the engines to use.
  2. The service records itIt checks the dataset exists, saves a comparison and one run per engine with status "queued", publishes ComparisonRequested, and answers right away.
  3. The orchestrator picks it upIt hears the event and sends each run to the worker pool. Two jobs can run at once. Each run gets a brand new process, so memory numbers stay clean.
  4. The runner drives the engineInside the worker, the pipeline runner calls the five stages in order and measures time, CPU and memory for each one.
  5. Progress flows backEach stage sends "started" and "done" events through a queue back to the event bus. The projector saves them, and the live stream shows them in your browser.
  6. The checker comparesWhen both engines finish, a separate job matches their outputs document by document and stores the verdict.
  7. The row tracker explainsFor every input row it records the outcome: delivered, rejected, duplicate or filtered out. The tracker page reads this.

The five stages

Both engines do exactly these steps, with the same rules and the same output.

1IngestRead the five tables from CSV or Parquet.
2CleanTrim text, parse dates and numbers, remove duplicates, fill safe gaps.
3ValidateCheck 13 rules. A trade that breaks any rule is rejected with its reasons.
4TransformFollow every link and write each trade as one nested JSON document.
5AggregateAdd up the exposure for each parent company.

DuckDB engine

Each stage is a SQL file. One query handles the whole table at once, spread over all CPU cores. Parent chains use a recursive query.

jq engine

Each stage is a few .jq programs. jq reads NDJSON one line at a time and makes several passes, building small lookup files between them. DuckDB converts the input to NDJSON first, because jq cannot read CSV or Parquet.

The patterns, in one line each

Strategyengines/duckdb_engine, engines/jq_engineTwo engines with the same five methods. The rest of the app does not care which one runs.
Template methodapplication/pipeline.pyThe runner fixes the order and the timing. Only the stage work changes per engine.
Factoryengines/__init__.pyGive it "duckdb" or "jq" and it hands back the right engine.
Ports and adaptersdomain/ports.pyInner code asks for an interface. Outer code provides the real thing.
Event busapplication/messaging.pyParts talk by announcing events, so the sender never waits for or knows the listener.
Projectionapplication/projections.pyOne listener turns events into the saved state of runs and comparisons. State always follows the events.
Repositoryinfrastructure/repositories.pySave and load records as JSON files, kept in memory for fast reads.
Process poolinfrastructure/workers.pyHeavy work runs in other processes, so the web server stays fast and one crash stays contained.
Composition rootapp/bootstrap.pyEverything is created and connected in one place, at startup.

Remember: requests only record and announce. Orchestrators do the work in worker processes, and events carry progress back.

Part 3 · The concepts

The words you will see

Two groups: the trade data the pipeline works on, and the moving parts of the app.

The trade data

Trade
One buy or sell of an instrument, by a book, with a counterparty, at a price and quantity.
Five tables
Trades, plus four lookup tables: counterparties, instruments, books and FX rates.
Amendment chain
A trade can point back to an earlier version of itself. The pipeline follows the chain and gives each one a version number.
Counterparty tree
Companies have parents, up to seven levels deep. Some trees loop by mistake, and the pipeline has to stop safely.
Ultimate parent
The top company of a tree. Exposure is grouped by it.
Exposure
Total value at risk with one parent company, in US dollars, counting only the latest version of each live trade.
Reject
A trade that broke at least one of the 13 rules. It goes to the rejects file with codes like E_PRICE_INVALID.
Warning
A problem the pipeline could fix or live with, such as a missing currency filled from the instrument. The trade is kept.
Dirty rate
How much mess the generator adds on purpose. The default is 2% of rows.

The app

Dataset
One set of the five tables, generated or uploaded. The same settings always give the same files.
Run
One engine processing one dataset through all five stages.
Comparison
The same dataset run on both engines, then checked for equal output.
Benchmark
Comparisons over several dataset sizes, one after another, with a summary table at the end.
Stage
One of the five steps. Each has its own time, CPU and peak memory numbers.
Event
A short message that something happened, like StageCompleted. Names ending in "Requested" ask for work. All others report facts.
Verification
Matching the two engines' outputs by trade id, allowing a cent of rounding. Above 200k rows it checks a fixed sample.
Row tracking
A table with the outcome of every input row. Rejected rows show up once validate is done, and all others when the run ends.
NDJSON
One JSON document per line. jq reads it line by line, and both engines write it as output.
Peak memory
The most RAM the run used at any moment, measured across the worker and any jq process it started.
Lean mode
A DuckDB setting that streams output and drops tables early. With insertion order turned off too, 1M rows went from 2.6 GB to 1.4 GB.
Spill
When DuckDB goes over its memory limit, it writes temporary data to disk instead of failing.

Remember: a dataset goes through a run of five stages. Two runs make a comparison, and several comparisons make a benchmark.
