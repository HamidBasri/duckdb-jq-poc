The last two words

Engine
The program that runs every mapping. This project has two, and each runs the whole pipeline on its own: DuckDB, a database that runs inside the app and speaks SQL, and jq, a command-line tool for JSON.
Verdict
For one kind of mapping, which engine runs it better, and why.
Our trade · in both engines

Both engines turn our trade into exactly the document from step 2, field for field. After every run a checker compares the two outputs document by document, and every run so far has matched. So a verdict is never about what comes out, only about how each engine gets there.

Two ways of working

What that means in practice

Speed

DuckDB is faster at every stage. At 1 million trades it took 11 s against jq's 5 min 14 s. Even limited to one core, DuckDB took 15.6 s.

Seeing ahead

DuckDB sees the whole table, so 4Look up and 5Walk work in any file order in one step. jq needs extra passes for the same thing.

Memory

jq only keeps what each pass needs: 632 MB at 1 million trades. DuckDB used 2.6 GB by default, or 1.4 GB once tuned.

Nested JSON

JSON is jq's native shape, so 5Walk on company trees and 7Nest read naturally. A SQL row can't contain itself, so DuckDB builds nested parents as JSON text.

The whole guide in five lines

  • 1 · Tables: five tables come in, linked by keys; only trades becomes documents.
  • 2 · Output: each valid trade becomes one document, with the rows it links to copied inside; bad trades go to rejects; exposures add documents up.
  • 3 · Mappings: every value travels by one of seven kinds: Clean, Parse, Fill, Look up, Walk, Calculate, Nest.
  • 4 · Problems: when a value doesn't fit, the trade is Fixed, Filled, Flagged, Dropped or Rejected.
  • 5 · Engines: both give the same result. DuckDB is better whenever a mapping needs the whole table, which is most of them. jq's strengths are memory and the two kinds where nested JSON is the natural shape.
